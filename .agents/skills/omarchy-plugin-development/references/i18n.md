# Plugin i18n reference

Use the copied Taskwarrior Time implementation as a working pattern for plugin translations. All new plugin UI must support **English and Spanish at minimum**. Add translations alongside each new user-visible string; do not leave secondary screens, tooltips, errors, dialogs, empty states, or settings untranslated.

## Required pattern

1. Put plugin-owned UI text in a translation module (for example `i18n.js`) with English as the fallback catalog and Spanish as a complete catalog. Other locales are optional.
2. Resolve `system` language from Qt's preferred UI-language list first, then locale name; normalize common forms such as `es-ES`, `es_ES.UTF-8`, and `es.utf8`. Fall back to English for unsupported system locales.
3. If the plugin exposes an override, accept only supported values (`system`, `en`, `es` at minimum), default to `system`, and persist through the plugin/host's existing settings mechanism. Do not add a subprocess or separate settings store solely for language selection.
4. Route every QML string through one translator function. If there is no override, system-locale selection alone is enough—do not add a language selector just because the reference About page has one.
5. Fall back from a missing translated key to English, then make a missing key visible to tests rather than silently returning an empty string.

Typical QML wiring (verify `Qt.locale()` behavior against the installed shell):

```qml
import "i18n.js" as I18n

property string uiLanguage: "system"
readonly property string localeName: {
  var loc = Qt.locale()
  if (loc && loc.uiLanguages && loc.uiLanguages.length > 0)
    return String(loc.uiLanguages[0])
  return loc ? String(loc.name || "") : ""
}

function tr(key) {
  return I18n.t(key, root.localeName, root.uiLanguage)
}
```

Use `root.tr("save")` for labels, buttons, placeholders, accessibility text, tooltips, notifications, empty/loading/error states, and plugin-generated process errors. Keep user data (task names, file names, remote values) as data; don't translate or interpolate it into rich text unsafely.

## Translation quality and checks

- Keep the English and Spanish maps key-complete. Adding a key to either catalog means adding its counterpart to the other in the same change. Test key parity; English fallback is runtime resilience, not a substitute for Spanish copy.
- Write idiomatic Spanish from Spain and clear English. Localize language names naturally (`English`, `Español`) and all About-page controls.
- Use placeholders for dynamic values and substitute them safely. The Taskwarrior example uses `%1` replacement for counts but has no plural-rule engine; add singular/plural keys or use a verified host plural API when grammar needs it.
- Test explicit English/Spanish selection, system `es` variants, preferred Qt UI language versus formatting locale, unsupported-locale English fallback, missing-key fallback, catalog completeness, and interpolation. If the user can persist an override, test reload/persistence using the existing settings path.
- Never make a successful check depend only on English fallback. Test rendered values from both catalogs for representative UI paths.

Taskwarrior Time's local examples are `tests/i18n.test.js` (locale resolution and overrides) and `tests/test_ui_language.py` (persisted Spanish setting). Its tests do not check catalog parity or plural grammar; add those checks in new plugins.
